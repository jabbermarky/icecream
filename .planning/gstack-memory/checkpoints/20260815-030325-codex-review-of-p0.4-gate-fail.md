## Working on: codex review of P0.4, gate FAIL

### Summary

A `/codex` consult reviewed the batch-loop design (`.planning/p0.4-batch-schema.md`
+ `.planning/batch-loop-design.md` against `.planning/binder-audit.md`) and returned
**GATE: FAIL — 13 [P1] findings, 2 [P2]**, 227k tokens. **Nothing has been fixed
yet.** The schema as written is not implementable. Four of the sharpest findings
were independently verified against the repo before being accepted. Tree is clean,
everything pushed, branch at `4751239`.

### Decisions Made

- **The P0.4 schema needs revision before B1 starts.** It was written in one pass
  from the binder audit and did not survive outside review. Do not begin
  implementation against the current text.
- **Codex was calibrated down on two findings, not accepted wholesale.** The
  atomicity finding (local IndexedDB + Drive cannot be atomic) is over-weighted for
  N=1 — local-commit-authoritative with eventual cloud consistency is the obvious
  resolution and matches decision 14's precedent. And "decisions 20 and 21
  contradict each other" is imprecise: no-prose-parsing and no-defect-taxonomy are
  compatible; the real muddle is inside decision 20 plus D2.
- **`.context/codex-session-id` is gitignored, not committed** (`4751239`) —
  machine-local codex thread id, stale on container reclaim, meaningless in a fresh
  clone. Matches how `.gstack/` is handled.
- **P1.2's phase line was corrected** (`f4ad253`): it still said "mechanical diff
  over ORDERED ingredient occurrences" after decision 18 settled that order is not
  meaningful.

### Remaining Work

1. **Revise the P0.4 schema against the 13 P1s.** They group into four work items:
   - **Snapshot durability.** `SnapshotRef` has no durable referent — nothing
     defines an immutable snapshot store or embedded container, so a later save
     leaves an old batch pointing at the wrong formula.
   - **Batch lifecycle rules.** Decision 16 contradicts decision 15 (reprint reuses
     the `planned` batch, so a second churn of the same snapshot cannot be
     recorded); reprint must name a `BatchId` and be a separate command from
     churn. Plus: no `SavedAt` on the batch record though decision 22 syncs it via
     the recipe pattern; no tombstones; no answer to "what happens to batches when
     a recipe is deleted", which P0.4 explicitly owes (batch-loop-design.md:536).
   - **The outcome instrument.** Missing viscosity/thickness axis; missing
     flavor-QUALITY axis (the audit line 94 explicitly warns that collapsing
     quality and intensity "loses the actionable half" — the schema collapsed it
     anyway); `overall` has no meaningful too-little/too-much semantics; the
     next-version delta `{target, direction, from, to}` cannot express a range
     ("fat 9-11% optimal") or a coupled constraint ("less dextrose, more sucrose,
     keep PAC, lower POD"); the prose contract is muddled between a typed open
     field and a photograph that would need out-of-scope OCR.
   - **Diff correctness.** The name-keyed diff collapses duplicate ingredient rows.
     Flagging coefficient drift is not enough — the audit wants recomputation under
     one coefficient set.
2. **Re-sequence.** Codex's proposed order: full B1 schema -> B2 local
   storage/deletion -> immutable snapshot contract -> P0.7+B3 atomic local print
   creation -> B5 sync -> P1.1 lineage -> B4/P1.2 diff -> settled attachment/text
   policy -> B6 and print-capture UI. B3 cannot precede P0.7; they are one cut.
3. **Deploy P0.3** (still not done, still the highest-value non-design item):
   verify cache-busting, reload every device, run
   `scripts/migrate-legacy-recipes.js` once per device.
4. Issues #15/#16 (~an hour each), then the UI replacement enablers (items 3, 8, 18).
