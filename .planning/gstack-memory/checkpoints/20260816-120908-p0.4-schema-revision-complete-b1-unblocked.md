### Decisions Made

**Shipped to production (both merged to `main`, which IS the deploy — Pages
serves the repo directly, no build step; both verified live by probing the site
rather than trusting the merge).**

- **PR #28 — the app reports its own build.** The version is a **bundle
  constant, not a fetched `package.json`**: the question the panel answers is
  "what code am I actually running", which matters most when a stale cache means
  the answer is "not what the server has". A fetched `package.json` would report
  the SERVER's version while the browser ran older JS. A unit test pins
  `APP_VERSION` to `package.json` — they had drifted two releases (hardcoded
  `"0.4.0 beta"` vs `0.5.0`). **`newer > 0` is the stale-cache detector**
  rollout step 1 could not otherwise perform.

- **PR #29 — the legacy migration moved into the app; the console script is
  DELETED.** Root cause: no browser on iPadOS has a console, so the one rollout
  step required on EVERY device was impossible on the primary one. Being in the
  app bought a review lane the script never had, and it had four real defects:
  it rewrote `SchemaVersion` unconditionally (downgrading records from future
  builds), restamped `SavedAt` (the author clock sync orders by), listed with the
  lossy `listRecipes` (a partial listing drains what it got and reports success —
  half a migration is worse than none, because nobody runs it twice), and
  duplicated `mintRecipeId` (now in `recipe-serialization.js`).

- **Rollout step 3 is now SYNC FIRST, then migrate.** The migration mints fresh
  ids, so a local legacy record whose synced copy is already identified would
  fork into a permanent `DIVERGENT_IDENTITIES` stall — a case that converges
  today. Syncing first lets those copies arrive already identified, so the
  migration leaves them alone. Converts the dangerous ordering into the safe one
  instead of warning about it.

- **The post-migration reload is required, not cosmetic.** `currentRecipeId` is
  null for a legacy record; after migration the store has an id and the page does
  not, so the next save would mint a SECOND id. The module cannot self-correct
  (the open recipe may have unsaved edits, or be a new recipe sharing a name), so
  the migration REFUSES to start when the recipe is modified and parks its
  summary in `sessionStorage` so the reload does not eat the report.

**P0.4 schema revision — `dc26016`, PR #25. All 13 P1s and both P2s resolved.**

Most findings were already answered by the 2026-08-15 maintainer session
(decisions 25–29 + `p0.4-data-model.mmd`); the stale artifact was the schema
*document*, still describing create-at-print, a fixed nine-axis outcome set and a
point-valued delta.

- **Decision 16 REVERSED**, superseded by decision 25. The amendment asked to be
  talked out of it on evidence that reference copies and cancelled prints are
  rare. **That evidence cannot exist:** the binder is a survivorship-filtered
  corpus of sheets that were churned AND filed, so a printed-never-churned sheet
  is not in it to count.
- **Decision 30:** the snapshot is **copied** into the batch, not referenced.
  Names the cost the amendment understated — mint-on-return makes the printed
  event carry the payload, so the pre-churn record moves rather than disappears.
- **Decision 31:** a batch is never deleted by its recipe. Closes the behaviour
  `batch-loop-design.md:536` said P0.4 owed.
- **Decisions 32, 33:** `overall` leaves the signed axis set; deltas group and
  carry a range plus a coupled constraint.
- **Decisions 34, 35:** the diff keys on `row_id` and **recomputes** under one
  coefficient set rather than only flagging drift.
- **Decision 36:** typed prose primary, photo an attachment, nothing parsed.
  **No OCR in scope.**
- Data model: `PRINT_LOG_ENTRY` becomes `RECIPE_EVENT` per decision 26, losing
  `chain_root` and `nudge_state` (killed by decision 25) and absorbing
  `TOMBSTONE`, since a deleted event IS a tombstone.

**Ingredient store — read out of the code, not remembered (`287ffe2`, `76218c7`).**
The maintainer raised schema versioning for the ingredient library; the gap is
wider. Recipes got `SchemaVersion` plus a fail-closed refusal gate in P0.3 and
the ingredient store got none of it, while still syncing: no `SchemaVersion`
anywhere on the path, the whole library is ONE record keyed `library` (the shape
decision 26 called fatal for the event log), `mergeIngredients` is a blind spread
with cloud winning unconditionally and no clock, the merge never removes so
deleted ingredients resurrect, and the store is keyed by mutable name (same class
as issue #19). **Urgent now because decision 35 requires the diff to recompute
under one coefficient set, and nothing in the library today can produce a
`coefficient_set_id`. B4 is blocked on this.** The blind cloud-wins merge is
filed as issue **#30**.
