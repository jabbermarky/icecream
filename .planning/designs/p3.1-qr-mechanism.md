# Printed sheet QR mechanism

*A record of a decision, not a plan. Current work: **#39**, which settles the
payload format — the one open question that accrues cost while it stays open,
because sheets printed against a format that later changes are unrecoverable
paper.*

**Author:** Mark Lummus
**Date:** 2026-08-15
**Status:** draft specification
**Depends on:** the batch minting on return (decision 25) and the snapshot being
copied into the batch rather than referenced (decision 30)
**Supersedes:** the single Quick Response ("QR") code payload described in the
earlier draft

---

## 1. Summary

The printed batch sheet carries two QR codes with different jobs and different failure consequences. Code A is small, heavily error-corrected, and carries only what the application needs to reattach a photographed sheet to the right record. Code B is larger, lightly error-corrected, and carries a self-description of the recipe so the page remains readable without the application. A human-readable short code sits beside Code A so that reattachment never depends entirely on optics.

The reason for the split is failure behavior. If Code B is unreadable, nothing is lost that Code A cannot recover from the database. If Code A is unreadable, the sheet is orphaned. Those two risks should not share a symbol.

---

## 2. Code A - identity

### 2.1 Payload

| Field | Type | Notes |
|---|---|---|
| `v` | uint8 | Payload format version, not `SchemaVersion` |
| `sv` | uint16 | `SchemaVersion` of the recipe container |
| `rid` | 16 bytes | `RecipeId`, raw UUID, not the hyphenated string |
| `pn` | 10 bytes | `print_nonce`, 80 bits of randomness |
| `ts` | uint32 | `printed_at`, Unix epoch seconds |

Total 33 bytes before encoding.

### 2.2 Symbol

Version 4 to 6, error correction level H, which tolerates approximately 30 percent damage. Module pitch at or above 0.6mm, giving a symbol of roughly 25mm square. Quiet zone of four modules on all sides.

Level H is chosen deliberately. This symbol will be photographed days after printing, from a page that has been on a counter next to a churning machine, possibly folded, at an angle, in kitchen light.

### 2.3 Placement

Top right of the sheet header. Outside the writing area, outside the horizontal thirds where a letter page folds, and not adjacent to any field the operator writes in.

### 2.4 Human-readable fallback

Print the first 40 bits of `print_nonce` as an eight-character code in Crockford base32, grouped as `XXXX-XXXX`, immediately below Code A in a monospaced face at 10pt or larger. Crockford base32 excludes I, L, O and U, so there is no ambiguity between characters that look alike in handwriting or in a poor photograph.

The operator must be able to type this code into the application and reach the same log entry that Code A resolves to.

## 3. Code B - archive

### 3.1 Purpose

Code B exists so that a printed sheet found in a binder in five years can be understood without the application, without the ingredient library, and without the coefficient set that produced it. The binder audit established that this is not a hypothetical - saved records outlived two generations of the ingredient model, and a page that cannot describe itself is a page that cannot be trusted.

Code B is never required at runtime. The application reads Code A and looks everything else up.

### 3.2 Payload

| Field | Type | Notes |
|---|---|---|
| `n` | string | Recipe name |
| `vl` | string | Version label |
| `m` | uint32 | Planned mass in grams |
| `rows` | array | Per row: ingredient name, grams, `duplicate_ordinal`, location |
| `tgt` | object | Target ranges for PAC, POD, serving temperature with unit, hardness, overrun |
| `calc` | object | Computed PAC, POD, fat, MSNF, total solids at print time |
| `cs` | string | `coefficient_set_id` |
| `cd` | 8 bytes | Digest of the coefficient values used, truncated SHA-256 |

Approximately 300 to 600 bytes for a twelve-ingredient recipe after compression.

### 3.3 Symbol

Version 15 to 20, error correction level M, roughly 45 to 55mm square at 0.5mm module pitch. Footer of the sheet.

### 3.4 The coefficient question

Code B carries `coefficient_set_id` and a digest of the coefficient values, not the coefficients themselves. Nine composition fields across twelve ingredients is over 500 bytes on its own and would force a third symbol.

The digest is the compromise. It does not let a future reader recompute, but it does let a future reader detect that the coefficients have changed, which is the failure the binder actually suffered. Dextrose PAC moved from 1.9 to 1.66 between application generations, and nothing on any page recorded that it had.

It is advisable to revisit this if a sheet format with more footer area is adopted.

## 4. Encoding

Byte mode, using deflated CBOR. Base64-encoded JSON is approximately three times larger for the same content and should not be used.

If alphanumeric mode is preferred for symbol size reasons, base45 is the correct encoding, since it packs more efficiently than base64 into the QR alphanumeric character set. Base45 exists for this purpose.

No Uniform Resource Locators ("URL"). A URL costs bytes that buy nothing, and a scanning phone will offer to open a browser rather than the application.

---

## 5. Return flow

1. The operator photographs or scans the sheet.
2. The application decodes Code A and resolves `print_nonce` against the print log.
3. On a hit, the application mints the batch, binds `print_nonce` to it, and marks the log entry `answered`.
4. The application loads the snapshot the log entry identifies, and capture begins against that snapshot.

### 5.1 Degradation

If the log entry is missing, because the sheet was printed on another device and the log has not synced, or because the entry was pruned, then Code A still carries `RecipeId`. The application mints the batch against the recipe, records the `print_nonce` as unresolved, and continues.

If Code A does not decode, the operator types the short code. If the short code is also lost, the operator selects the recipe manually and the sheet is attached as a photograph with no binding.

If Code B does not decode, nothing happens. Code B has no runtime consumer.

Each step degrades to something usable. That is the point of the split.

---

## 6. Printing constraints

Quiet zone of four modules on all sides of both symbols.

Never scale a symbol to fit available layout space. If a symbol does not fit at its specified module pitch, the layout is wrong, not the symbol.

Print at 600 dots per inch or better. At 300 dpi a 0.5mm module is approximately 6 dots, which is workable but leaves no margin for a marginal printer.

Pure black on white. No background tint, no watermark behind either symbol, no color.

Keep both symbols clear of the horizontal thirds of the page.

---

## 7. Test cases

The following should pass before the QR mechanism is considered done.

A sheet photographed at 30 degrees off perpendicular under a single overhead kitchen light decodes Code A.

A sheet with a 20mm opaque spot over one corner of Code A decodes Code A.

A sheet folded in thirds and flattened decodes both symbols.

A sheet photographed after seven days in a binder decodes both symbols.

The short code, typed manually with no scan, resolves to the same log entry as Code A.

A sheet whose log entry has been deleted still mints a batch bound to the correct recipe.

## 8. Open items

Whether the print log syncs across devices. If it does not, a sheet printed on the desktop will not resolve on the phone, and section 5.1 degradation becomes the normal path rather than the exception.

Whether `print_nonce` needs 80 bits. Collision risk at any plausible print volume is negligible at 48 bits, which would save four bytes in a payload where bytes are scarce.

Whether Code B should carry the method steps, which are not currently in the schema at all. A roasting step that is not on the page is a step the sheet cannot describe.

Whether a third symbol carrying full coefficients is justified on a sheet format with more footer area.
