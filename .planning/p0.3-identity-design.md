# P0.3 — Where recipe identity lives

**Status:** REVIEWED AND DECIDED (eng review + outside voice, 2026-08-12).
The first draft of this document recommended Option A with a local index and
claimed zero sync changes; the review kept Option A, corrected both of those
claims, and merged P0.6's identity guards into this cut. History below is
preserved; the decisions section is authoritative.
**Unblocks:** P0.4 (batch records), P0.6 (now shrunk — see decision 6), P0.7
(print an identified snapshot).

`.planning/batch-loop-design.md` marked P0.3 **DO NOT START** over two unsolved
problems. This document resolves them. P0.3's DO-NOT-START marker lifts when
this design's decisions are reflected there.

---

## The question

A recipe needs a stable identity that survives rename, distinguishes a copy
from the original, and is the same identity on every device. Today identity
*is* the name: IndexedDB keys on it (`indexeddb-storage.js:192`), Drive encodes
it in the filename (`google-drive-storage.js:60`), and sync joins the two sides
by it (`sync-manager.js:113-114`).

Where does the id go?

---

## What the code forces

These are constraints, not preferences. All were re-verified line-by-line by
the outside voice.

### C1. One Drive file is the only atomic unit in the system

`updateFile` is a single `PATCH` of one file's whole body
(`google-drive-storage.js:431-445`). There is no transaction spanning two
files. Anything that must stay consistent with a recipe has to be *inside that
recipe's file*, or it can be observed out of step with it. (Corollary, found
in review: that PATCH uses `uploadType=media`, which **never rewrites
`appProperties`** — any metadata mirror of identity can silently go stale
against its own file body.)

### C2. Sync moves `data` and nothing else

```js
// sync-manager.js:122
await cloudStorage.saveRecipe({ name: local.name, data: recipe.data });
```

Same on the pull side (`:145`, `:161`). A field not inside `data` does not
cross the network. (Second corollary, found in review: the join itself runs
over `listRecipes()` output, which is `{name, updatedAt}` on both sides —
IndexedDB at `indexeddb-storage.js:74`, Drive parsing names out of *filenames*
at `google-drive-storage.js:141-151`. A field inside `data` syncs for free and
is exactly as invisible at join time.)

### C3. Sync is automatic, unattended, and last-write-wins

`handleAuthStateChange` runs a full `syncAll()` on sign-in with no
confirmation (`sync-manager.js:36-52`); conflicts resolve on `updatedAt`
(`:129-131`). And the clock is rotten: both stores re-stamp `updatedAt` at
write time (`indexeddb-storage.js:32`, `google-drive-storage.js:63`) and the
Drive side compares file `modifiedTime` (`:149`), so a pull immediately makes
local look "newer" and the next sync pushes identical bytes back. Decision 8
gives the container a truthful clock.

### C4. The only merge precedent in the codebase reassigns values silently

`mergeIngredients` is cloud-wins per key, no report (`sync-manager.js:220-229`).
Applied to an identity map it would let the cloud reassign which id a recipe
has. No identity map is synced under this design.

### C5. P0.2 already built an anti-truncation gate

`containerProblem` refuses a newer `SchemaVersion` before any mutation
(`recipe-serialization.js:205-216`); `hydrateRecipe` returns null rather than
truncating (`:246-257`). It protects every client built **after** P0.2. A
client built **before** P0.2 has no gate — a transitional threat, closed
operationally (decision 2).

### C6. The hydrator filters to declared `cRecipe` fields

`for (const key in recipe)` over a fresh `cRecipe`
(`recipe-serialization.js:253-255`). Container-level fields are safe from it;
recipe-level fields are not. Identity therefore lives at container level and
never on `cRecipe` — which also means `copyFrom`'s `Object.assign`
(`core.js:108`) cannot clone an id by accident.

## Options considered

### Option A — identity in the container (CHOSEN)

```js
{
  SchemaVersion: 2,
  RecipeId: "…",              // crypto.randomUUID(), minted once at save
  SavedAt: "2026-…T…Z",       // author-time clock, stamped by the builder
  Recipe: { … },               // unchanged, declared-fields filtered
  Ingredients: { … }
}
```

Atomic with the recipe by construction (C1); rides `data` so it crosses the
network with no new sync *entity* (C2); a LWW conflict picks one whole record,
identity included (C3); no synced map, so no merge policy for one (C4);
`SchemaVersion: 2` makes every post-P0.2 client refuse rather than truncate
(C5); container-level, so the hydrator and `copyFrom` never touch it (C6).

Two claims from the first draft, corrected in review:

- ~~"Zero changes to sync-manager.js or google-drive-storage.js"~~ — true only
  while the join stays name-based. The id-first join (decision 3) is a real,
  costed sync change; what remains true is that identity *transport* needs no
  sync changes.
- ~~"The local store demotes to a derived index"~~ — the index is **dropped
  from P0.3 entirely** (decision 5). Its strip-detection job targets a threat
  closed operationally, its semantics under delete/name-reuse rebuilt the
  blocker-2 resurrection bug inside the mitigation, and sync pulls
  (`sync-manager.js:145`, `:161`) bypass any incremental maintenance. It
  returns in P0.4 if batch references need it, designed against real
  requirements.

**Blocker 2 (delete/name-reuse) resolves** — not because a mechanism fixes it,
but because nothing keyed by name outlives the record anymore. Identity dies
with the record; a new record minting a new id is the *correct* outcome for a
genuinely new recipe reusing an old name.

### Option B — separate store, synced as its own file (REJECTED)

Recipe and identity become two files with no transaction between them (C1). An
ordinary partial sync — push the recipe, fail before the identity file — leaves
device two unable to distinguish "identity not arrived" from "none", so it
mints one: one recipe, two ids, lineage forked silently. Trades a transitional
threat (pre-P0.2 stale tab) for a routine one, and needs tombstones, a
generation counter, and a map merge policy on top.

### Option C — both, container authoritative, store mirrors (REJECTED)

Two synced copies of one fact need a reconciliation policy for when they
disagree — the bug class this design exists to avoid, bought against a threat
that is one stale browser tab.

## Decisions (review + outside voice, all resolved)

| # | Decision | Rationale anchor |
|---|---|---|
| 1 | **Identity lives in the container** behind `SchemaVersion: 2`, as `RecipeId`, never on `cRecipe`. Id format: `crypto.randomUUID()`. | C1, C6 |
| 2 | **The pre-P0.2 strip threat is closed operationally, not architecturally.** At rollout of the v2 build: close/reload every open tab of the app on every device, and verify the deploy does not serve the old bundle from cache (hard reload or cache-busted assets). After that, every live client has the refusal gate and the window is shut permanently. The doc claims no in-app detection beyond decision 7's warning. | C5 |
| 3 | **Sync joins id-first with name fallback.** Implementation: when a candidate pair lacks a known id on either side, the join downloads the cloud file body to see one — dozens of small JSON files at this scale. No `appProperties` mirror (see C1 corollary; filed as an optimization todo with the staleness trap documented). | C2 corollary |
| 4 | **Ids are minted on SAVE only, never on load.** A legacy record stays unidentified until first save; loads never write. Prevents the migration-time fork where N devices each stamp their own ids on shared records before sync reconciles. P0.7 must handle (or force-save) the unidentified case at print time. | C3 |
| 5 | **No local index in P0.3.** Id lookups are a record scan. The index, if ever needed, arrives with P0.4's batch references. | outside voice 4+5 |
| 6 | **P0.6's identity guards ship IN this cut** — the mainline save-as-new-name flow (`recipe-manager.js:1283`, `:1299`) would otherwise create two records carrying one id on day one, and the name-only overwrite prompt (`:1289-1294`) can silently destroy a different recipe's id. The mint rule — **AMENDED in T2.5** (cross-model KEEP verdict; the original "different-id overwrite is a copy and mints" letter was written about the rename flow and over-reached it): **a save mints when keeping the id would put it on two local records; otherwise identity follows the recipe.** So the rename-copy flow mints (the old record keeps the id), while a confirmed overwrite by an imported recipe whose id nothing else carries KEEPS its id — preserving batch-history attachment and letting the id-first sync join converge instead of manufacturing duplicates. Overwrite of a record carrying a different id (including by an UNIDENTIFIED recipe — T2.5) re-prompts naming the real stakes. P0.6 shrinks to the explicit copy button and the rename-refusal UI. | outside voice 2+3; codex 1a/1b |
| 7 | **A v2 record with missing/garbage `RecipeId` loads with a warning and re-mints on next save.** It is NOT refused: the payload is intact and the plausible cause (stale client) is not the user's fault. Consequently RecipeId validation lives **outside** `containerProblem` — the fail-closed gate must not refuse what decision 7 loads. Any future restore affordance is a user-confirmed action through the normal save path, never a write triggered from load. | outside voice 7+8 |
| 8 | **`SavedAt` (author-time, stamped by `buildRecipeContainer`) travels in the v2 container.** Both stores re-stamp `updatedAt` at write time and Drive LWW compares `modifiedTime`, so the existing clock lies (C3). The merge module compares `SavedAt` when both sides carry one, `updatedAt` as legacy fallback — same shape as the id join. Added now because the schema is already being cracked open; later would cost a v3. | outside voice 6 |
| 9 | **The join/merge decision is extracted into a pure module before the sync change lands** — given local and cloud record lists (ids optional), decide push/pull/conflict/copy per record. Same extraction pattern as `recipe-library-load.js`, which has caught criticals three times on this branch. The module's spec MUST cover: duplicate ids on one side (decision 6's window, pre-guard records), a dead id colliding with a live name, legacy no-id records on either side, **and a schema guard (T1 review, red team): sync overwrites records it never loads, so the module must never let an older-schema writer overwrite a record whose SchemaVersion it does not understand — skip and surface a sync warning instead. Without this, a stale device's LWW push strips v2+ fields wholesale on a path the load gate cannot see.** | outside voice 1+3, Issue 5, T1 review |
| 10 | **In-memory identity home:** module state in `recipe-manager.js` alongside `recipeStorage`; **cleared in `handleNewRecipe`** (`recipe-manager.js:1120-1129` currently has no such line — it needs one). Set on load, carried to save, never on `cRecipe`. | C6 |
| 11 | **`.ier` import with an id:** same id already in the library → an import-time prompt, keyed by id (T2.5: "this file is the same recipe as X — load as that recipe, or as an independent copy?"; copy adopts null and mints at the next save). Same name but different id resolves at save under decision 6's amended rule. The `.ier` envelope stays v1 — the container's own SchemaVersion 2 is what pre-P0.2 builds cannot check, and that population is closed by decision 2. | batch-loop open decision 3; codex 2 |
| 12 | **Typed arrays (and ArrayBuffers) are REFUSED at snapshot time** — explicit reversal of the P0.5 pin that passed them through unfrozen. The T1 review showed they are not storable but silently corrupted: JSON backends turn `Uint8Array([1,2,3])` into `{"0":1,...}` while IndexedDB stores the real thing, and the next sync pull overwrites the good copy. Same policy as functions: loud refusal, nothing written. Future photo support (P3.3) uses a separate Blob store by design, not recipe fields. | T1 review, maintainer |
| 13 | **The library "Saved" column keeps showing `updatedAt` for now** — routing `SavedAt` to it is user-visible and Phase 0 is structural-only. Filed as a todo (`.planning/todos/pending/2026-08-12-library-saved-column-savedat.md`). | T1 review, maintainer |

## What P0.3 now contains

1. `recipe-serialization.js`: v2 container (`RecipeId`, `SavedAt`), id
   validation outside the gate, hydration leaves identity at container level;
   `RECIPE_SCHEMA_VERSION` → 2.
2. `recipe-manager.js`: identity module state + `handleNewRecipe` clear; mint
   on save; copy-mints / overwrite-re-prompts guards (decision 6); warn path
   (decision 7).
3. Pure join/merge module (decision 9) with its full unit matrix — landed and
   tested BEFORE `sync-manager.js` calls it.
4. `sync-manager.js`: swap the name-join for the module (id-first, name
   fallback, body download when an id is unknown) — **and route `pushRecipe`
   (the fire-and-forget path) through the same guards** (codex finding 3: it
   is a second write path that would otherwise bypass the join entirely, and
   it currently reports success even when `saveRecipe` returns false — #12).
5. Rollout note in the PR: reload every device, verify cache-busting.

## Known windows until T3/T4 (recorded in the codex outside-voice round)

- **The identity scan is local-only** — a cloud-only carrier of an id is
  invisible until the join lands, so a second device's record can share an id
  with a cloud record it has never seen. Closed by T3/T4.
- **The overwrite decision is TOCTOU** across the confirm/scan awaits (item
  20's family, already filed): a sync pull can replace the target between
  read and put. The put, not the prompt, must become the guard point.
- **`loadRecipe` conflates not-found with read-error** (backends swallow,
  #12's family): a transient read failure bypasses the overwrite and
  newer-schema guards. Needs a backend interface distinction; scoped with #12.

## Rollout — what has to happen at deploy (T6, 2026-08-14)

P0.3 changes the shape of every record the app writes. Three steps, in order,
plus one limit to know about. None of it is code; all of it is the operational
half of decisions 1 and 7.

1. **Verify cache-busting BEFORE announcing the deploy.** Step 2 is worthless if
   a reloaded device still fetches the old JS. Confirm the app's asset
   references actually change between builds; a device that "reloaded" while
   still running v1 code is the exact hazard step 2 exists to remove, now
   wearing a badge that says it is safe.
2. **Reload every device — every browser, every tab — before anyone saves.**
   This is the operational closure the maintainer chose over code. Identity
   lives in the container, so a stale tab running pre-P0.3 code hydrates only
   the `cRecipe` fields it knows and writes the truncated object back, stripping
   `RecipeId` from a record the new code created. The container gate refuses
   newer schemas, but a v1 client predates the gate — it cannot refuse what it
   does not know exists. There is no code fix for a tab that is already open.
   The window is bounded by the deploy, not permanent, and decision 7 makes the
   consequence recoverable rather than silent: a stripped record loads with a
   warning and re-mints on its next save, losing only that record's link to
   batch history.
3. **Tap "Give older recipes an identity" on Info & FAQ, once per device,
   after reloading.** Decision 14 makes legacy conflicts REJECT — an id-less
   body never replaces an identified record. Until every local record carries
   an id, a legacy record that collides warns
   (`SYNC_WARNINGS.LEGACY_CONFLICT`) on *every* sync and does not merge. Do
   not skip it and wait for the warnings to stop on their own — by design,
   they will not.

   *Amended 2026-08-16.* This step used to be `scripts/migrate-legacy-recipes.js`,
   pasted into a DevTools console. That made the one step required on EVERY
   device impossible on the maintainer's primary device: no iPad browser has a
   console. It is now `js/features/legacy-migration.js` behind a button on the
   panel that reports the legacy count, and the script is deleted. Being in the
   app also bought review it never had: it duplicated `mintRecipeId`, and it
   rewrote `SchemaVersion` unconditionally, which would have DOWNGRADED a record
   written by a future build.

**Known limit, unchanged by P0.3: deletes do not propagate across devices.**
There are no tombstones, so deleting a recipe on one device does not delete it
anywhere else, and the next sync from any device still holding a copy brings it
back. This is pre-existing behavior and is banked as item 14 of the round-3
review file. It is written here because identity changes how the resurrection
*looks*: the record returns carrying its original `RecipeId`, so it comes back
as the same recipe rather than as a duplicate — better than the alternative, but
still a return from the dead. Delete on every device, or expect it back.

## Decision 14 — legacy conflicts REJECT; no graft (maintainer, 2026-08-14)

The codex T3 cross-model round found that the name-fallback join let an
id-less record beat an identified one on the clock and erase its identity
fleet-wide. Four resolutions were weighed (skip+warn, id-always-wins, graft,
graft+warning); graft-with-warning was proposed. The maintainer rejected the
whole frame: **for an app with N=1 users, merge semantics for unlikely format
collisions are not worth design time.** The rule as shipped:

- An id-less body NEVER replaces an identified record, whichever way the
  clock leans — `SYNC_WARNINGS.LEGACY_CONFLICT`, both in `planRecipeSync`
  (name-fallback pass) and `decideRecipePush`. Handled on an exception
  basis: the warning tells the user to keep one copy and delete or rename
  the other. (The messages deliberately do NOT say "re-save and sync
  again" — a re-save mints a FRESH id, which converts the conflict into a
  permanent `DIVERGENT_IDENTITIES` stall, not a resolution.)
- The other direction stays open: an identified winner replacing a legacy
  record is how old records get carried forward.
- The Info & FAQ migration (`js/features/legacy-migration.js`) drains the
  legacy population so the refusal stops firing at all. Run it on the device
  whose recipes are current: it mints FRESH ids, so migrating a legacy copy
  whose cloud counterpart is already identified forks the lineage into the
  divergent-identities stall — the confirm prompt carries that caveat.

Known costs, accepted: a genuinely-newer legacy edit stalls at the warning
until a human re-saves it (this is the point — exception basis); and the
remaining codex P2 findings (key/body name mismatch classified as rename,
equal-clock rename divergence never surfaced) are banked in
`.planning/todos/pending/2026-08-13-t2.6-round3-review-findings.md` for the
merge-boundary review, not designed around now.
