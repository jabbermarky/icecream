# P0.3 — Where recipe identity lives

**Status:** design proposal, not yet decided. Written to be reviewed.
**Blocks:** P0.4 (batch records), P0.6 (copy mints identity), P0.7 (print
persists an identified snapshot). Every remaining Phase 0 task needs identity,
so this document is the only thing between the batch loop and more code.

`.planning/batch-loop-design.md` marks P0.3 **DO NOT START** and names two
unsolved problems. This document takes them seriously enough to cost the
alternatives against the code that exists, rather than the code we imagine.

---

## The question

A recipe needs a stable identity that survives rename, distinguishes a copy
from the original, and is the same identity on every device. Today identity
*is* the name: IndexedDB keys on it (`indexeddb-storage.js:192`), Drive encodes
it in the filename (`google-drive-storage.js:60`), and sync joins the two sides
by it (`sync-manager.js:113-114`).

Where does the id go?

---

## What the code forces

These are constraints, not preferences. Any design has to survive them.

### C1. One Drive file is the only atomic unit in the system

`updateFile` is a single `PATCH` of one file's whole body
(`google-drive-storage.js:431-445`). There is no transaction spanning two
files, no batch endpoint in use, and no ordering guarantee between two
independent writes. Anything that must stay consistent with a recipe has to be
*inside that recipe's file*, or it can be observed out of step with it.

### C2. Sync moves `data` and nothing else

```js
// sync-manager.js:122
await cloudStorage.saveRecipe({ name: local.name, data: recipe.data });
```

Same on the pull side (`:145`, `:161`). The Drive record is
`{name, updatedAt, data}` (`google-drive-storage.js:61-65`). A field that is
not inside `data` does not cross the network. This is the mechanism behind the
design doc's blocker 1, and it is exact: not "sync would need work" but "the
field is not in the payload".

### C3. Sync is automatic, unattended, and last-write-wins

`handleAuthStateChange` runs a full `syncAll()` on sign-in with no user
confirmation (`sync-manager.js:36-52`). Conflicts resolve by comparing
`updatedAt` (`:129-131`). Nobody is watching when identity is decided.

### C4. The only merge precedent in the codebase reassigns values silently

`mergeIngredients` takes local, then overwrites per key from cloud
(`sync-manager.js:220-229`) — cloud wins, no report. If an identity *map* were
synced, this is the shape the next author would reach for, and applied to
identity it means the cloud can reassign which id a recipe has.

### C5. P0.2 already built an anti-truncation gate

`containerProblem` refuses a container whose `SchemaVersion` exceeds what this
build understands, before any mutation (`recipe-serialization.js:205-216`), and
`hydrateRecipe` returns null rather than truncating (`:246-257`). This is the
mechanism the design doc wanted a separate store for — it already exists, and
it works for both backends and the `.ier` file at once.

Its limit is precise: it protects against every client built **after** P0.2. A
client built **before** P0.2 has no gate and will still hydrate-and-truncate.

### C6. The hydrator filters to declared `cRecipe` fields

`for (const key in recipe)` over a fresh `cRecipe`
(`recipe-serialization.js:253-255`). A field not declared on `cRecipe` is
dropped on hydration — which is *why* container-level fields (`SchemaVersion`)
are safe from it and recipe-level fields are not.

---

## The two problems the design doc raised

**Blocker 1 — identity does not sync.** Direct consequence of C2. A separate
store is not part of `data`, so device two finds a recipe with no identity and
allocates its own. The doc's own words: *"no sync changes" is untenable for
identity specifically.*

**Blocker 2 — keying by name bites on delete and reuse.** Delete the mapping
and a resurrected recipe gets a fresh id; keep it and a genuinely new recipe
reusing that name inherits a dead one. The doc proposes tombstones plus
permanent name non-reuse, or keying by id with a name index and a generation
counter.

Worth naming plainly: **blocker 2 is a property of the separate store, not of
identity.** It exists because a map keyed by name outlives the record it
describes. It does not arise if identity dies with the record.

---

## Option A — identity in the container

Identity becomes a container-level sibling of `Recipe` and `Ingredients`,
behind a schema bump:

```js
{
  SchemaVersion: 2,
  RecipeId: "r_01J...",        // minted once, never rewritten
  Recipe: { ... },              // unchanged, still declared-fields filtered
  Ingredients: { ... }
}
```

`buildRecipeContainer` gains identity as an explicit argument, exactly as it
already takes the ingredient library. Identity is *not* a `cRecipe` field: it
is a property of the record, not of the formula, and keeping it off `cRecipe`
keeps it out of reach of the declared-fields filter (C6) and preserves P0.5's
rule that one path owns container shape.

The local store still exists, demoted to a **derived index**: `id → name`,
`name → id`, and later the batch references P0.4 needs. It is rebuildable by
scanning records, and it is never the authority.

**Against the constraints:**

- C1 — identity is in the file. Atomic with the recipe by construction.
- C2 — rides inside `data`. **Zero changes to `sync-manager.js` or
  `google-drive-storage.js`.**
- C3 — a last-write-wins conflict picks one whole record, identity included.
  The record never disagrees with its own id.
- C4 — no map is synced, so no merge policy is needed.
- C5 — `SchemaVersion: 2` makes every post-P0.2 client refuse rather than
  truncate. The gate is already written and already tested.
- C6 — container level, so the hydrator never sees it.

**Blocker 2 dissolves.** Identity lives in the record and dies with it. Delete
the recipe, the id is gone. Create a new recipe that reuses the name, it mints
a new id. No tombstones, no generation counter, no permanent name reservation.

**What it does not solve:** a **pre-P0.2** client — a browser tab left open
since before this branch ships — has no refusal gate. It hydrates the v2
record through its own declared-fields filter, drops `RecipeId` along with
`SchemaVersion`, and writes the truncated container back. Identity is lost
silently.

Mitigation is detection, not prevention: the local index still holds
`name → id`. On load, a record whose name the index knows but which carries no
`RecipeId` is a strip. Report it and offer to restore from the index rather
than silently re-minting. That is the index earning its place.

**Cost:** small. `buildRecipeContainer` takes a third argument; `containerProblem`
validates `RecipeId` shape; app state tracks the open recipe's identity; the
index store is a new IndexedDB object store with no sync surface. Ships behind
one `RECIPE_SCHEMA_VERSION` bump.

## Option B — separate store, synced as its own file

The design doc's current call, made syncable: a third Drive file
(`identities.json`) alongside `ingredients.json`, plus a new sync entity in
`syncAll()`.

**Against the constraints:**

- C1 — **fails.** Recipe and identity are two files with no transaction. Push
  the recipe, fail before pushing identities (network drop, token expiry, tab
  closed — `pushRecipe` is fire-and-forget, `sync-manager.js:236-249`), and
  device two pulls a recipe whose identity does not exist yet. It has no way to
  distinguish "identity not arrived" from "no identity", so it mints one. Now
  one recipe has two ids and the lineage forks. This is the failure the whole
  feature exists to prevent, and it is reachable by an ordinary partial sync.
- C2 — needs new sync code by definition.
- C3 — the identity map syncs last-write-wins against a second device's map.
- C4 — needs a merge policy for the map, and the precedent in the file
  reassigns silently.
- C5 — irrelevant, which is the point: it protects against pre-P0.2 clients
  too, since they cannot strip a store they do not know exists.

**Blocker 2 stands** and needs the tombstone/generation machinery the doc
describes.

**Cost:** meaningfully larger. New Drive file, new sync entity, a merge policy
for an identity map, tombstones, a generation counter, and `.ier` import has to
reject same-name/different-id collisions. Every one of those is a place to be
wrong.

**What it buys:** immunity to the pre-P0.2 stale-tab strip.

---

## Option C — both, container authoritative, store mirrors

Identity in the container (Option A) *and* a synced store (Option B) as a
redundant copy, used to restore what a legacy client strips.

**Against the constraints:** inherits A's clean answers for C1–C3 and C6, and
adds B's exposure on C4 — two synced copies of one fact need a reconciliation
policy for when they disagree. That policy is the same class of bug this
document exists to avoid, now with more surface.

**Cost:** A plus B, plus reconciliation.

**What it buys:** recovery from a pre-P0.2 strip without user involvement.

---

## Comparison

| | A — in container | B — separate synced store | C — both |
|---|---|---|---|
| Syncs at all | Free (rides `data`) | New sync entity | Free + new entity |
| Atomic with the recipe | Yes, by construction | **No** | Yes, for the authoritative copy |
| Partial sync mints a duplicate id | No | **Yes** | No |
| Needs a map merge policy | No | Yes | Yes |
| Delete / name-reuse (blocker 2) | Dissolves | Tombstones + generation | Tombstones + generation |
| Survives a pre-P0.2 stale tab | Detect, not prevent | Prevent | Recover |
| Files changed | serialization, save path, new local index | those + sync-manager + drive + merge policy | all of the above |

---

## Recommendation

**Option A.**

The reasoning is C1. Identity has to be consistent with the recipe it
identifies, and in this system the only thing that is written atomically is one
recipe's file. Putting identity anywhere else means accepting that the two can
be observed out of step — and the consequence of being out of step is not a
stale read, it is a **second identity minted for the same recipe**, which
forks lineage permanently and silently. Option B trades a rare failure (a stale
tab that predates this branch) for a routine one (any interrupted sync).

The separate store was proposed to solve legacy truncation. P0.2 already
solved legacy truncation for every client built after it (C5), which is the
population that actually exists once this ships. Paying B's cost to also cover
pre-P0.2 clients is paying a permanent architectural price for a transitional
threat.

Option A also makes the residual risk *observable*, which the doc's version
does not: the local index gives a name→id expectation, so a stripped record is
a detectable event with a message, not a silent re-mint.

## Sub-questions this design does not yet settle

These want an answer before code, and are the right target for review:

1. **Id format.** ULID-like sortable string, `crypto.randomUUID()`, or
   `name + timestamp`? Only requirement so far: generated client-side, no
   coordination, safe in a filename if identity ever reaches the Drive name.
2. **Where is the open recipe's identity held in memory?** Module state in
   `recipe-manager.js` alongside `recipeStorage`, or threaded through
   `getRecipe()`. It must survive load → edit → save without living on
   `cRecipe`, and must be cleared by `handleNewRecipe`.
3. **Does `containerProblem` reject a v2 record with a missing or malformed
   `RecipeId`?** Refusing is consistent with the module's fail-closed rule;
   accepting-and-reminting is friendlier and looser. This is a real fork.
4. **What does `.ier` import do with an id?** A file carrying an id that
   already exists locally is either a re-import of the same recipe or a copy.
   The envelope-version question in the design doc (open decision 3) collides
   with this.
5. **Legacy records have no id.** Mint on first save, or mint on load? Minting
   on load makes every open a write; minting on save leaves records unidentified
   until touched, and P0.7 needs an id at print time.
6. **Does the index rebuild automatically?** A scan on startup is cheap for a
   hobby-scale library and makes the index genuinely disposable. It also runs
   before sync, which matters for strip detection.
7. **Rename refusal (P0.6) still stands** and this document does not change it.
   Sync joins by name (C2/`:113`), so rename A→B on one device while another
   holds A offline still republishes A, giving two names one id. Identity in
   the record makes that *detectable* on the next sync rather than invisible,
   but it does not prevent it.

---

## Test plan (whichever option wins)

The unit lane drives the real handlers, so these are all reachable without a
browser:

- A v2 record round-trips through library save → load with its id intact.
- A v2 record round-trips through `.ier` export → import with its id intact.
- Save does not mint a second id for a recipe that already has one.
- Copy mints a different id (P0.6); rename does not change one.
- A record whose name the index knows but which carries no id is reported as a
  strip, not silently re-minted.
- `containerProblem` behaviour for a v2 record with a missing/garbage id,
  whichever way sub-question 3 goes.
- Identity survives the save-time snapshot: the id written is the one from the
  container, not one read live across the awaits (the P0.5 rule, applied to the
  new field).
- Per review item 22, at least one browser test round-trips a container built
  by `buildRecipeContainer` — a container-shape regression currently ships
  green in both lanes, and this change *is* a container-shape change.
