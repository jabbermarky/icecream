## Why this file exists

The T2.5 → T2.6 review loop ran three rounds (2026-08-13). Rounds one and two
were applied and landed (`a178054`, `611bab0`). Round three returned five
findings, deliberately NOT applied — the maintainer chose to bank the loop and
move to T3. Until this file they existed only in conversation context. Severity
is converging: round one had live-bug classes, round two robustness edges,
round three is one behavioral edge plus polish. All five are candidates for the
merge-boundary full /review before #11 lands.

## The findings

1. **Duplicate Recent Recipes entries for an unnamed recipe**
   (`recipe-manager.js:168`). `BackupRecipe` no longer renames the live recipe
   (T2.6 follow-up: it names the stacked COPY only), so backing up the same
   unnamed recipe twice — import hits the replace modal → "Keep Current" →
   `RestoreBackup` backs up again — lands two identical copies under two
   different random names. The old in-place rename made the second call reuse
   the first key and overwrite. Needs a small design call; leading option:
   `BackupCurrentRecipe` propagates the generated name back to the on-screen
   recipe (the wrapper knows it holds the live recipe), keeping `BackupRecipe`
   itself pure.

2. **Replace-modal button handlers escape `reportApplyFailure`**
   (`recipe-manager.js:~1706`). The modal's onclick handlers run after
   `applyImportedFile` returns, so a throw in `RestoreBackup` /
   `DisplayBackupList` inside them reaches neither the promise `.catch` nor the
   sync try/catch — modal stuck open, no error shown. Fix: wrap both onclick
   bodies, `hideModal` in a finally.

3. **`BackupRecipe`'s `modified` parameter defaults to `IsRecipeModified()`**
   (`recipe-manager.js:165`) — module editor state, so an off-screen caller
   omitting the argument silently records the on-screen recipe's flag. The same
   hidden-module-state pattern T2.5/T2.6 closed for identity. Fix: drop the
   default; make `BackupCurrentRecipe`/`RestoreBackup` pass it explicitly.

4. **Stale NOTE in `recipe-serialization.js:~401`** — the hydrateRecipe
   frozen-container note still says `importIngredients` runs before hydration
   on the .ier import path; T2.6's follow-up inverted that order in
   `handleLoadRecipeFile` (hydrate-first, matching `recipe-library-load.js`).
   Doc-only; update the first-casualty analysis.

5. **Duplicated error-message construction** — `'The recipe could not be
   imported: ' + (err && err.message ? err.message : err)` lives in both
   `finishLoad`'s catch and `reportApplyFailure`. Extract one formatter taking
   an optional suffix so the two user-facing messages for the same failure
   class cannot diverge.

## Context worth keeping

- One review claim from round two was WRONG in an instructive way: moving
  `SetRecipeModified(false)` before `DisplayRecipe` broke the browser suite —
  `DisplayRecipe` drives the sliders' `oninput()` handlers, which mark the
  recipe modified, so clear-after-display is load-bearing everywhere. The
  landed shape is a `finally` on the render phase. The stub-DOM unit lane
  cannot see this (stub sliders throw before `oninput`); only the browser
  suite catches it.

## Banked from the codex T3 cross-model round (2026-08-14, decision 14)

The round's P1s were resolved by decision 14 (legacy conflicts REJECT — landed
with tests) and by T4's two executor rules (recorded in the design doc's T4

maintainer's N=1 scope call; candidates for the merge-boundary /review only.

6. **Key/body name mismatch classified as a rename** (item-18 family) — a
   record whose storage key and `Recipe.Name` disagree joins under whichever
   name the caller listed, and the join can plan a "rename" for a record
   nobody renamed. Simple fix if ever needed: classify key≠body-name records
   unreadable-style (skip + warn) in `classifySide`.

7. **Equal-clock rename divergence never surfaced** — same id, different
   names, `compareClocks === 0` → counted `unchanged`, no warning; the names
   diverge silently forever. Simple fix if ever needed: warn on
   `cmp === 0 && names differ` in `resolvePair`.

8. **Ingredient-free recipes fall out of the mid-scan backup guarantee** —
   `BackupRecipe` refuses any recipe with `Ingredients.length == 0`
   (`recipe-manager.js`), so the import path's "backup before overwrite"
   promise silently skips ingredient-free recipes. Adjacent to item 3's
   BackupRecipe design call — resolve together.

## Banked from the T4 full review round (2026-08-14, five passes:
## testing/maintainability/security specialists + Claude adversarial + codex)

Applied that round (for the record): Drive listing pagination, query-value
escaping in `findFileByName`, anchored filename decode, listRecipes→Strict
DRY inversion both backends, IndexedDB strict listing off the lossy
`updatedAt` index, `executeGatedPush` extraction + tests, delete failures
fold into sync status + surface as warnings, auth-burst 'already syncing'
no longer paints error, warning batching for the single status-bar slot.
These nine were deliberately NOT applied — design calls or N=1-gated:

9. **Sync's own rename residue stalls as DUPLICATE_ID forever** (adversarial
   F2, conf 8). A skipped or failed rename-delete leaves old+new records
   sharing one id; the next sync's `resolveDuplicateIds` excludes and BLOCKS
   the stale one and the planner never deletes excluded entries, so one
   transient delete failure warns on every future sync until hand-fixed.
   Interacts with executor rule 2 (any write failure skips ALL deletes,
   widening the trigger). Fix needs the join to recognize "own rename
   residue" (same id, strictly older, loser-name of a surviving pair) —
   a deliberate T3-semantics change, so a design call, not a patch.
   Mitigated meanwhile: status shows error + a delete-failed warning tells
   the user to remove the copy now (applied this round).
10. **Deletes execute by mutable name, not file id** (codex 2): a record
    created at the old name between plan and delete is destroyed. Needs a
    second concurrent writer inside the sync window — N=1 gate; falls with
    item 9's design call and item 12's id-based loading.
11. **Push gate fails open on Drive read errors** (codex 3 / adversarial F3
    leg): drive `loadRecipe`/`downloadFile` swallow errors to null, which
    `fetchCloudRecordForPush` must read as "absent". Documented on the
    function; closing it is #12's backend not-found/read-error distinction.
    Same ticket: `decideRecipePush` never clock-compares a same-id push
    (delayed replay of an older body needs a retry queue that doesn't exist).
12. **Listing ids are fetched and discarded; bodies load serially by
    reconstructed name** (adversarial F6, codex 5/8): id-based loading would
    kill the duplicate-filename and name-round-trip fragility class and the
    N+1 Drive round-trips. Design change to the store interface; N=1 perf
    is fine today.
13. **Drive duplicate filenames conflate into one body** (adversarial F4):
    `findFileByName` pageSize:1 returns an arbitrary one of N same-named
    files. Needs concurrent creates (N=1 gate) or F3-class failures (now
    escaped); real fix is item 12.
14. **Deletes never propagate across devices** (adversarial F10): no
    tombstones, so a deleted recipe resurrects from any device still holding
    a copy. Pre-existing semantics; T6's rollout note already owes the
    deleted-record resurrection sentence — reference it there.
15. **Warning dedup across syncs** (adversarial F8 remainder): batching per
    sync applied, but stalled states re-warn every sync by design (they ARE
    unresolved). Session-level dedup by code:side:name if it gets noisy.
16. **`SYNC_OPS`/`SYNC_TARGETS` constants** (maintainability): executor and
    planner share the 'push'/'pull'/'delete'/'local'/'cloud' vocabulary as
    bare literals; export frozen constants like SYNC_WARNINGS if either side
    ever grows a new op.
17. **Test fixture dedup** (maintainability): `v2()`/timestamps copy-pasted
    across recipe-sync-join.test.js and recipe-sync-executor.test.js;
    extract a shared fixture module when next touched.
18. **syncAll's result→status mapping has no unit test** (testing): the
    executor side is covered; the manager mapping (writeFailures/
    deleteFailures → success/'error') lives in browser-only sync-manager.
    Extract a pure `syncOutcome()` if it grows another input.

## Redesign triage (2026-08-14, maintainer context: the UI/UX is being replaced)

A UI replacement is in progress (some pages already redesigned). Every item
below — plus the two remaining P0.3 tasks — is tagged so the merge-boundary
review can sort what survives the swap from what the swap deletes.

### Tag rubric

**Domain tags** (not mutually exclusive):

| Tag | Means |
|---|---|
| `[UX]` | the finding is about what the user sees or does — a surface, a message, a modal, a list |
| `[BIZ-LOGIC]` | core domain rule: identity, save/mint, join, backup guarantee |
| `[LEGACY]` | revolves around id-less / pre-v2 recipes |
| `[SYNC]` | cross-device join/executor/store semantics |
| `[DATA-LOSS]` | a realized bug destroys or silently drops a user's recipe |
| `[TEST]` | the deliverable is coverage, not behavior |
| `[DOCS]` | paperwork only |
| `[CODE-HEALTH]` | internal quality, no behavior change |
| `[PERF]` | round-trip count / latency |

**Disposition tag** (exactly one per item — this is the axis the redesign needs):

| Tag | Means |
|---|---|
| `[REDESIGN-DEFER]` | the fix lives in code the redesign rewrites. Don't patch it now; carry the *rule* into the redesign's requirements or the patch is thrown away. |
| `[REDESIGN-ENABLER]` | fixing it makes the swap safer — it pulls logic out of UI/editor state so the new surface inherits a clean API. Do these **before** the new UI is wired. |
| `[REDESIGN-INDEPENDENT]` | lives below the UI (`js/storage/`, `js/models/`). Untouched by the swap; schedule on its own merits. |

### What the tags say

**No `[LEGACY]` item is left in the banked set.** Decision 14 closed that class
outright — an id-less body never replaces an identified record — and the
remaining legacy work is the throwaway `migrate-legacy-recipes.js` run, which
is a T6 rollout line. The redesign inherits no legacy-recipe debt.

**Ten of eighteen are `[REDESIGN-INDEPENDENT]`, and they are where the
`[DATA-LOSS]` tags cluster** (10, 11, 13, 14, plus 8). `js/storage/` and
`js/models/` were built as pure modules precisely so a UI swap could not reach
them, and the tagging confirms that held: the sync correctness backlog is
entirely portable. Item 9 is still the sharpest of these and does not get
easier by waiting.

**The three `[REDESIGN-ENABLER]`s share one shape:** each moves a decision out
of hidden editor/module state or browser-only code into something a new surface
can call. Item 3 (`modified` defaults to `IsRecipeModified()`), item 8
(`BackupRecipe` silently refusing ingredient-free recipes, so the
backup-before-overwrite promise does not hold), and item 18 (extract a pure
`syncOutcome()` out of browser-only sync-manager). Items 3 and 8 are the same
`BackupRecipe` design call and were already flagged to resolve together — that
call is now on the redesign's critical path, not merely adjacent to it. These
are the only banked items worth doing *before* the new UI is wired.

**Five `[REDESIGN-DEFER]`s are patches that would be thrown away** (1, 2, 5, 15,
and T5-as-specified). The rules behind them are not throwaway, and each should
land as a requirement on the new surface rather than as a fix on the old one:
a backup of an unnamed recipe must reuse its key rather than mint a second
entry (1); every async handler attached to a modal must report its own failures
and dismiss in a `finally` (2); one formatter owns the import-failure message
(5); and warnings need somewhere to queue (15). Item 15 is the same problem as
`.planning/todos/pending/2026-01-15-toast-notifications.md` — the single-slot
status bar is a constraint of the *current* UI, and the batching applied in the
T4 round is a workaround for it. If the redesign brings a real notification
area, item 15 dissolves and the batching code should be revisited, not kept.
