## Why this file exists

The T2.5 → T2.6 review loop ran three rounds (2026-08-13). Rounds one and two
were applied and landed (`a178054`, `611bab0`). Round three returned five
findings, deliberately NOT applied — the maintainer chose to bank the loop and
move to T3. Until this file they existed only in conversation context. Severity
is converging: round one had live-bug classes, round two robustness edges,
round three is one behavioral edge plus polish. All five are candidates for the
merge-boundary full /review before #11 lands.

## The findings

1. **Duplicate Recent Recipes entries for an unnamed recipe**
   (`recipe-manager.js:168`). `BackupRecipe` no longer renames the live recipe
   (T2.6 follow-up: it names the stacked COPY only), so backing up the same
   unnamed recipe twice — import hits the replace modal → "Keep Current" →
   `RestoreBackup` backs up again — lands two identical copies under two
   different random names. The old in-place rename made the second call reuse
   the first key and overwrite. Needs a small design call; leading option:
   `BackupCurrentRecipe` propagates the generated name back to the on-screen
   recipe (the wrapper knows it holds the live recipe), keeping `BackupRecipe`
   itself pure.

2. **Replace-modal button handlers escape `reportApplyFailure`**
   (`recipe-manager.js:~1706`). The modal's onclick handlers run after
   `applyImportedFile` returns, so a throw in `RestoreBackup` /
   `DisplayBackupList` inside them reaches neither the promise `.catch` nor the
   sync try/catch — modal stuck open, no error shown. Fix: wrap both onclick
   bodies, `hideModal` in a finally.

3. **`BackupRecipe`'s `modified` parameter defaults to `IsRecipeModified()`**
   (`recipe-manager.js:165`) — module editor state, so an off-screen caller
   omitting the argument silently records the on-screen recipe's flag. The same
   hidden-module-state pattern T2.5/T2.6 closed for identity. Fix: drop the
   default; make `BackupCurrentRecipe`/`RestoreBackup` pass it explicitly.

4. **Stale NOTE in `recipe-serialization.js:~401`** — the hydrateRecipe
   frozen-container note still says `importIngredients` runs before hydration
   on the .ier import path; T2.6's follow-up inverted that order in
   `handleLoadRecipeFile` (hydrate-first, matching `recipe-library-load.js`).
   Doc-only; update the first-casualty analysis.

5. **Duplicated error-message construction** — `'The recipe could not be
   imported: ' + (err && err.message ? err.message : err)` lives in both
   `finishLoad`'s catch and `reportApplyFailure`. Extract one formatter taking
   an optional suffix so the two user-facing messages for the same failure
   class cannot diverge.

## Context worth keeping

- One review claim from round two was WRONG in an instructive way: moving
  `SetRecipeModified(false)` before `DisplayRecipe` broke the browser suite —
  `DisplayRecipe` drives the sliders' `oninput()` handlers, which mark the
  recipe modified, so clear-after-display is load-bearing everywhere. The
  landed shape is a `finally` on the render phase. The stub-DOM unit lane
  cannot see this (stub sliders throw before `oninput`); only the browser
  suite catches it.
